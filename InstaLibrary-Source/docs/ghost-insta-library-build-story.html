A LOCAL-FIRST CAMERA PROJECT

我做了一个不依赖官方 App 的 Insta360 素材库

从一个打不开的相机网关开始，经过协议观察、只读约束、视频 Range 代理和 WebGL 全景预览，最后把它装进了两套可以直接分发的 macOS App。

Wi-Fi DirectRead-only UCD2React + PythonApple Silicon / Intel本地优先

事情的起点其实很朴素：相机就在桌上，SD 卡里有几百个素材，电脑也已经连上相机 Wi-Fi。我只想像打开 NAS 一样浏览它们，而不是每次都先打开手机 App、导入、等待，再想办法把文件送到电脑。

01 · 起点

相机开了热点，却不等于它有一个网页后台

最自然的尝试，是让 Mac 连上相机热点，然后在浏览器中访问网关地址。常见的局域网设备往往会在网关上放一个管理页面，至少也会暴露某种目录索引。但这台相机不是路由器：网关能被系统识别，不代表根路径能在浏览器里打开，更不代表文件系统会像 WebDAV 一样出现。

我最初花了一些时间验证 HTTP 根路径、常见端口和目录形式，结果都指向同一个事实：浏览器访问网关这条路，从模型上就错了。相机提供的是“给官方客户端使用的服务”，而不是“给用户浏览的网页”。

第一个转折点

“网关进不去”不是网络没有连接，而是连接之后还缺少控制协议、会话状态与真实文件路径。继续猜 URL 的收益已经很低。

02 · SDK 黑盒

官方文档告诉了我能力边界，却没有给出协议细节

Insta360 的 iOS SDK 文档明确列出了相机连接、参数读取、拍摄、文件列表、下载和导出等能力。它还提到 Wi-Fi Socket 的建立与心跳机制。这些信息很重要：至少说明相机不是只能被手机识别，它确实存在一条稳定的控制通道。

问题在于，SDK 本体是二进制。能调用，不等于能看到它怎样组帧、怎样校验、怎样关联请求与响应。对我的目标来说，引入这个 SDK 还有另一个现实问题：我想做的是一个 macOS 本地工具，而不是再造一遍官方 iOS App。

文档回答了“它能做什么”，但我真正需要回答的是“电脑最少要说哪几句话，才能安全地拿到文件列表”。

于是思路从“下载 SDK”变成了“观察一个已经工作的客户端”。这不是去破解相机，也不是绕过账号或加密；目标只是理解本机与自有设备之间已经发生的通信，以完成只读互操作。

03 · 观察

在一次次断网之间，把实验压缩到最小

连接相机 Wi-Fi 后，电脑通常就失去互联网。这让远程协作式排查变得很笨重：连相机、执行命令、断开相机、恢复网络、发送结果，然后重复。做了几轮之后，我开始把每次实验写成一次性脚本，让它在离线期间完成连接、记录、解析和保存，恢复互联网后只需要查看结果。

STEP 01确认设备地址与开放端口

区分“热点网关存在”和“应用协议可用”这两件事。

STEP 02观察官方 App 的控制流量

只记录连接、读取选项和读取文件列表，不触发拍摄或设置修改。

STEP 03离线重放最小请求

固定使用已经观察到的读取帧，验证相机是否给出一致响应。

STEP 04把响应变成可审计的数据

拆分帧边界、序列号、状态与 Protobuf 负载，再提取文件路径。

STEP 05产品化

把控制会话封装为本机 API，让网页只处理素材列表和媒体 URL。

这个调整节省的不只是实验次数。它迫使每一步都有清楚的输入和输出，也避免在相机在线时临时尝试含义不明的命令。

04 · 协议

只理解完成任务所需的那一小块 UCD2

捕获到的控制消息以 ASCII 字节 UCD2 开头。对这个项目而言，不需要写出一份“完整私有协议规范”，只需要可靠地完成三件事：识别完整帧、取得内部请求序列号、解析文件列表响应。

观察到的消息结构OBSERVED, NOT OFFICIAL SPEC
MagicUCD2
4 bytes Meta版本 / 类型
4 bytes Lengthlittle-endian
4 bytes Payload命令、序列号、状态、Protobuf Integrity保留捕获值
4 bytes

尾部完整性字段没有足够样本可以可靠推导。我没有“猜一个 CRC 再试试”，而是保留官方 App 已经发出并经实机验证的固定帧。这样做不够灵活，却让允许发送的内容可以逐字节审计。

ALLOWED_COMMANDS = {8, 13}

def send_readonly(sock, frame):
    command = inner_request_code(frame)
    if command not in ALLOWED_COMMANDS:
        raise RuntimeError("read-only policy rejected command")
    sock.sendall(frame)

当前允许列表中，命令 8 用来读取设备与存储选项，命令 13 用来读取文件列表。其他命令一律在写入 Socket 之前拒绝。心跳也使用固定捕获帧，负责让只读控制会话保持在线。

“只读”必须是代码结构，不是一句免责声明

项目没有拍摄、录像、删除、格式化、改参数和同步时间的入口。即使页面被错误操作，也不存在能走到这些命令的发送路径。

05 · 架构

网页负责体验，本机服务负责接近设备

浏览器不能直接连接任意 TCP Socket，也不应该知道私有帧。最终结构被拆成五层：App 只负责启动和退出，Web UI 负责交互，Python API 持有控制会话，相机的控制端口返回目录，相机的 HTTP 服务传输具体文件。

06 · 文件目录

“超过 500 张”不是一个单纯的前端分页问题

最初的读取帧只有五页，每页最多 100 条，因此文件数一多就会停在 500。界面做成每页 300 项，并不能凭空让后端发现第 501 个文件。

应用现在会先尝试读取相机 HTTP 目录索引。如果固件开放目录，就可以取得完整列表；若目录索引关闭，才降级到五个固定 UCD2 分页帧，并把“可能截断”的状态明确交给页面。这里没有把不完整结果包装成成功。

DISCOVERY目录发现

HTTP 索引优先，固定读取帧作为兼容性降级。

RENDERING页面分页

每页最多 300 项，只控制浏览器渲染与交互负担。

SAFETY路径白名单

媒体代理只接受本次目录中出现过的完整路径。

def assert_known_path(self, path):
    if path not in self.files:
        raise ValueError("path is not in the current camera file list")
07 · 产品化

当素材真的有几百个，界面问题才刚开始

第一版只要能把文件名列出来就算成功。但真正连接相机后，列表很快就暴露出另一组问题：照片没有秩序、视频不知道内容、快速滚动时一屏灰块、批量下载要逐个点击。

于是界面逐步增加了日期分组、当天全选、跨页选择、搜索、类型筛选和每页 300 项。视频缩略图优先读取同名 LRV 低码率代理，既节省热点带宽，也比直接解码原视频更快。

骨架屏也可能拖慢滚动

一页 300 个卡片如果同时加载媒体、同时执行 shimmer 动画，浏览器的网络、解码和合成线程会一起忙起来。现在所有卡片先立即画出静态几何占位，只有靠近视口约 1400 像素的项目才开始请求资源，动画也只在这个范围内运行。

const observer = new IntersectionObserver(onVisible, {
  rootMargin: "1400px 0px"
});

// 接近视口后才真正挂载 img / video
{active && <MediaVisual file={file} />}

这里追求的不是“尽快把 300 张图都下载完”，而是快速滑动时屏幕始终有稳定结构，并把有限带宽留给用户马上要看的内容。

08 · 媒体预览

视频要能拖进度，360 照片要能转动视角

视频弹窗使用浏览器原生控制条，但真正让时间轴可拖动的是后端的 Range 转发。浏览器请求某个字节区间，API 把 Range 原样交给相机，再回传 206 Partial Content 与 Content-Range。用户跳到几分钟之后时，不必先下载整个文件。

如果 MP4 或 INSV 能匹配到 LRV，播放器优先使用 LRV；页面上的“下载原文件”仍然指向原始素材。预览速度和最终文件质量因此被分成了两个独立选择。

一个很小的 WebGL 全景查看器

照片加载后先检查宽高比。接近 2:1 的等距柱状图进入 360° 模式；普通照片继续平面展示。全景模式没有引入大型播放器库，而是让片元着色器把屏幕像素反投影成空间方向，再换算为经纬度纹理坐标。

const ratio = image.naturalWidth / image.naturalHeight;
const panorama = ratio >= 1.8 && ratio <= 2.2;

longitude = atan(direction.x, direction.z);
latitude  = asin(direction.y);

鼠标或触控拖动会更新 yaw 与 pitch，滚轮改变视场角。实现时还有一个很容易忽略的细节：相机全景图通常不是 2 的幂尺寸，而 WebGL 1 对这类纹理的环绕方式有限制，因此必须使用 CLAMP_TO_EDGE，否则部分设备上只会得到一块黑色画布。

全景查看不等于全景拼接

这个查看器面向已经转换为 2:1 等距柱状格式的图像。双鱼眼原片仍然需要镜头模型、标定参数和拼接算法，仅靠在浏览器里旋转纹理无法得到正确空间视角。

09 · 打包

“双击能用”比开发服务器多了很多工作

开发阶段运行一条 Python 命令没问题，但把软件发给朋友时，不能假设对方安装过 Python、Node、npm 或任何依赖。最终的 App 把运行时、生产网页、协议代码、Protobuf 和许可证全部放进包内。

可复现构建流水线ARM64 + X86_64
01前端生产构建生成 server/client bundle
02下载目标运行时对应架构 Node 与 Python
03生成图标从源码 PNG 生成 ICNS
04组装 App启动器、代码、依赖、许可
05签名与压缩验证后用 ditto 生成 ZIP

Apple Silicon 与 Intel 版本不是只改了文件名：原生启动器、Node 和 Python 都是对应架构的 Mach-O。构建脚本会自动下载目标运行时，所以一份源码可以生成任一架构，也可以一次生成两套。

tools/build_distributions.sh arm64
tools/build_distributions.sh x86_64
tools/build_distributions.sh all
10 · 踩坑

两个最像“小问题”的 Bug，恰好都发生在交付之后

页面只剩文字

第一次把前端放进 App 后，HTML 能打开，界面却像 1995 年的网页一样只剩文字。资源都在包里，问题出在内置服务器：它把 /assets/... 相对路径当成无效 URL，CSS 和 JavaScript 全部返回 404。

修复不复杂——给相对路径补一个本机基准 URL，并在应用路由前直接处理静态资源。真正重要的是后来增加了成品级检查：不只测试首页返回 200，还要验证 CSS、JS 的 MIME、内容和状态码。

App 启动一次后，签名失效

另一个问题更隐蔽。刚打包时深度验签完全通过，但启动一次后再验签，就提示密封资源被修改。原因是 Python 在 App 包内部写入了 __pycache__。程序本身照样能跑，可签名完整性已经被破坏。

export PYTHONDONTWRITEBYTECODE=1

禁止写入字节码缓存后，验证流程也改为“构建后验签 → 实际启动 → 正常退出 → 再次验签”。这比单纯看到编译成功可靠得多。

11 · 源码交付

源码包必须真的能离开我的电脑

把项目文件复制进 ZIP 不等于可复现。一次独立解压测试暴露出打包脚本仍在引用原项目里旧 App 的图标，而且最早版本要求本机 Node 必须同时包含 arm64 与 x86_64。这些条件在我的电脑上成立，到了朋友电脑上却未必成立。

现在图标由源码 PNG 现场生成，目标 Node 和 Python 运行时按架构下载，Git 元数据、node_modules、虚拟环境和构建缓存不会进入源码包。最后的验证是在一个临时目录中解压源码 ZIP，安装依赖，再从那里独立构建出新的 Apple Silicon App。

我对“源码可用”的定义

不是文件齐全，也不是主项目能编译，而是压缩包离开原目录后，按照 README 的命令仍能产出通过签名检查的 App。

12 · 边界

现在能做什么，还不能做什么

能力状态说明
读取相机文件目录支持HTTP 目录优先，固定只读帧降级。
照片、视频缩略图支持接近视口时加载；视频优先 LRV。
视频播放与拖动支持依赖浏览器可解码格式与 Range 响应。
360° 照片拖拽支持 2:1 全景不包含双鱼眼原片拼接。
DNG 浏览器解码不支持保留原文件下载。
删除、拍摄、修改参数刻意不实现保持只读安全边界。
所有相机与固件需要逐机验证不同型号可能有不同目录和命名行为。
无警告公开分发尚未公证正式发布需要 Developer ID 与 Apple 公证。

最后，它从“绕开 App”变成了一个完整的小产品

回头看，最难的部分并不是写出某个解析函数，而是在每个阶段都守住边界：不知道的字段不猜，没观察过的命令不发，不完整的目录不假装完整，能在我电脑上运行的源码也不急着称为可分发。

这个项目最终没有替代官方软件的全部能力。它只是把一个高频、明确的动作做得更直接：连接自己的相机，打开自己的素材，预览，然后下载。对我来说，这已经足够有价值。
